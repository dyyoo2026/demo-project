`SubscriptionRenewalService` 테스트 22개를 새로 작성했고 모두 통과합니다. 버그로 판단한 것은 없지만, 결제 실패 쪽에서 확인이 필요한 설계 이슈가 2개 있습니다(아래 "확인이 필요한 부분").

- **파일:** `tests/test_renewal.py` (테스트 22개, 파라미터 케이스 포함)
- **실행:** `.venv/bin/python -m pytest -v` → 25 passed(기존 3 + 신규 22), 0 failed

### 결정한 사항 (질문할 수 없어서 직접 정함)
- **기존 관례를 따름:** 기존 `tests/test_models.py`처럼 pytest 함수 스타일과 영어 테스트 이름을 쓰고, `conftest.py`의 `make_subscription` 팩토리를 그대로 썼습니다. 섹션 주석은 프로젝트 docstring에 맞춰 한국어로 달았습니다.
- **시간 고정:** venv에 freezegun이 없어서 의존성을 추가하지 않았습니다. 대신 `monkeypatch`로 `billing.renewal.datetime`을 2025-03-01 09:00 UTC로 고정했습니다.
- **협력 객체 대역**
  - Repository: 작은 Fake를 썼습니다. `save` 시점의 상태를 deepcopy로 기록하기 때문에, 실패 횟수를 올리기 전에 저장하는 식의 순서 버그도 잡힙니다.
  - `PaymentClient` / `Notifier`: `create_autospec`을 써서 메서드 시그니처가 틀리면 바로 실패합니다.
- **로그 메시지:** 운영용 세부사항이라 검증하지 않았습니다.

### 커버한 동작
- **대상 선정**
  - 현재 UTC 시각으로 `find_due`를 호출합니다.
  - 대상이 없으면 빈 리포트를 반환합니다.
  - CANCELLED / SUSPENDED 구독은 결제·저장·알림 없이 `skipped`로 분류합니다.
  - 저장소가 아직 만료되지 않은 구독(1초 남음)을 돌려줘도 `skipped`로 분류합니다.
  - 만료 시각이 정확히 지금인 구독은 갱신합니다(경계값).
- **결제 성공**
  - `charge("user-7", 14900, idempotency_key="sub-42:20250228")`: 연장 전 만료일로 키를 만듭니다.
  - 만료일을 기존 만료일 기준으로 30일 연장합니다(현재 시각 기준이 아님).
  - 실패 횟수를 0으로 초기화하고, history에 `renewed: tx-…`를 남깁니다.
  - `renewal_success` 알림에 새 만료일을 담아 보냅니다.
  - 리포트의 `renewed`에 들어갑니다.
- **결제 거절 (`PaymentError`)**
  - 1회차 실패: 1회로 저장되고 `remaining_attempts=2`, 2회차 실패: 2회로 저장되고 `remaining_attempts=1`. 상태는 ACTIVE를 유지하고 `failed`로 분류됩니다.
  - history에 `failed: <사유>`를 기록하고, 만료일은 연장하지 않습니다.
  - 3회차 실패(경계값)
    - SUSPENDED로 전환되고, history에 `suspended: <사유>`를 기록하고, `suspended`로 분류됩니다.
    - `subscription_suspended` 알림만 1회 보냅니다(`renewal_failed`는 보내지 않음).
  - 한 구독의 결제 거절이 배치의 다른 구독 처리를 막지 않습니다.
- **결제사 장애 (`PaymentGatewayUnavailable`)**
  - 실패 횟수, 상태, 만료일, history가 모두 그대로이고 저장도 알림도 하지 않습니다.
  - 배치를 즉시 중단합니다. 뒤 구독은 결제하지 않고, 뒤에 있는 CANCELLED 구독도 `skipped`에 넣지 않습니다.
  - 장애 전에 처리한 결과(갱신, 거절 모두)는 저장과 리포트에 그대로 남습니다.
- **혼합 배치:** 갱신 / 거절 / 정지 / 건너뜀이 각자 맞는 리스트로 분류됩니다.

### 테스트 강도 확인
프로젝트를 임시 디렉터리에 복사해서 변이 17개를 넣어 봤습니다. 원본 프로덕션 코드는 건드리지 않았습니다.

- 잡힌 변이 16개
  - `>=` → `>`
  - 장애 시 `break` → `continue`
  - 성공 시 실패 횟수를 초기화하지 않음
  - 멱등키 형식 변경
  - 남은 횟수 off-by-one
  - 상태 필터 / `is_due` 검사 제거
  - 실패 횟수를 올리기 전에 저장
  - 시각을 naive `utcnow`로 변경
  - 그 밖의 변이
- 살아남은 1개는 동작이 원본과 똑같은 변이(`extend(0)`)라 의미가 없습니다.

### 확인이 필요한 부분 (버그로 단정하지 않음)
1. **결제 거절 후 재시도에 같은 멱등키를 씀** (`billing/renewal.py:75`)
   - 키가 `"{구독ID}:{만료일}"`인데 `PaymentError`가 나면 만료일이 그대로입니다. 그래서 2회차, 3회차 재시도도 같은 키(`sub-1:20250301`)로 결제를 요청합니다.
   - 결제사가 같은 멱등키의 응답을 캐시한다면(Stripe 등은 거절 응답도 캐시합니다), 사용자가 카드를 바꿔도 재시도가 실제로 일어나지 않습니다. 캐시된 거절을 3번 받고 정지될 수 있습니다.
   - docstring에 적힌 형식대로 동작하고 있어서 테스트는 현재 동작 기준으로 썼습니다. 결제사의 멱등키 동작을 확인해 보시고, 필요하면 키에 시도 횟수를 넣는 방안(예: `{id}:{YYYYMMDD}:{failed_attempts}`)을 검토해 보세요.
2. **알림·저장 예외나 예상 밖 결제 예외를 처리하지 않음** (`renewal.py:86-87, 91-96, 103-104`)
   - 결제가 성공한 뒤 `notifier.send`가 예외를 던지면 배치 전체가 중단됩니다. 나머지 구독은 처리되지 않고 리포트도 반환되지 않습니다.
   - `charge`가 `PaymentError` / `PaymentGatewayUnavailable`이 아닌 예외를 던질 때도 마찬가지입니다.
   - docstring에 정책이 없어서 테스트로 고정하지 않았습니다. 알림 실패를 갱신과 분리할지 정해 주시면 테스트를 추가하겠습니다.

### 커버하지 않은 부분
- 위 2번의 예외 전파 동작: 정책이 정해지지 않아 고정하지 않았습니다.
- 오래전에 만료된 구독(예: 두 달 전 만료)의 따라잡기 결제: 현재는 기존 만료일 + 30일이라 연장 후에도 과거 날짜로 남고, 다음 배치에서 또 결제됩니다. docstring과는 일치하지만 의도한 동작인지 확인해 보시면 좋겠습니다.
